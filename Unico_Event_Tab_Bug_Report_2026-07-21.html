1 Firebase messaging init throws a runtime TypeError on every Event page load HIGH

Location src/services/firebase-messaging.js:46, called from src/app/application-layout.jsx:270 (initializeFirebaseMessaging)
Description On load, onMessage(messaging, …) is called while messaging is null (Firebase messaging unsupported / permission not granted in this context). This throws and surfaces as the red "1 Issue" Next.js dev overlay on the page.
Error Runtime TypeError: Cannot set properties of null (setting 'onMessageHandler')
Steps to reproduce
  1. Open any Event page, e.g. http://localhost:3000/events/1017
  2. Observe the red "1 Issue" badge (bottom-left); click it to view the stack trace.
Expected: Page loads with no runtime error; messaging init no-ops when unsupported.
Actual: TypeError thrown from firebase-messaging init on every load.
Suggested fix: Guard before subscribing — if (messaging) { onMessage(messaging, …) } — and/or await isSupported() before initializing.

2 Order refund status contradicts itself HIGH

Location Order List → order detail (example order #273345)
Description The order header and the Order Timeline show "Refund In Progress" (timeline marks it as Current), while the Refund Information block on the same page shows Status "Refunded". The two states contradict each other, so staff cannot tell whether the refund is complete.
Steps to reproduce
  1. Event Tab → Order List (/events/orders).
  2. Open a "Refund In Progress" order (e.g. #273345) via ⋯ → View.
  3. Compare the header/timeline status with the "Refund Information → Status" field.
Expected: A single, consistent refund status across header, timeline, and Refund Information.
Actual: Header/timeline = "Refund In Progress"; Refund Information = "Refunded".
Suggested fix: Derive all three from one source of truth for refund state; reconcile the order status once the reversal is confirmed.

3 Attendee name shows a status string instead of a name MEDIUM

Location Order detail → Registrations table
Description In the Registrations table, the attendee Name column displays "Awaiting Payment" — a status value leaking into the name field — while the same row shows Payment = "Paid" and Status = "Registered". The name is wrong and the values are internally inconsistent.
Steps to reproduce
  1. Open an order detail (e.g. /events/orders/273345).
  2. Scroll to the Registrations section and read the Name column.
Expected: Real attendee name; Name and Payment fields consistent.
Actual: Name = "Awaiting Payment" while Payment = "Paid".
Suggested fix: Populate Name from the attendee record; fix the fallback that substitutes a payment status into the name field.

4 Edit Event form does not preload the existing cover image MEDIUM

Location Event Planning → ⋯ → Edit (/events/planning/{id})
Description An event that already has a cover image (visible on its detail page) opens the Edit form with an empty "Upload a file or drag and drop" dropzone. The current image is not shown, risking accidental loss of the image on save and giving no indication one exists.
Steps to reproduce
  1. Open an event that has a cover image (e.g. "New Testing Event").
  2. Click Edit Event (or ⋯ → Edit on the planning list).
  3. Observe the Cover Image field shows an empty upload area, not the current image.
Expected: Existing cover image (and other saved media/values) preloaded in the edit form.
Actual: Cover Image dropzone is empty despite an image existing.
Suggested fix: Hydrate the form with the event's current cover image URL and show a thumbnail with replace/remove.

5 Internal developer text visible in the production UI MEDIUM

Location Edit Event form → "Basic Information" section
Description The Basic Information section displays the helper line "Map these fields to the add-event API payload." — an internal developer note that should not be shown to merchants.
Steps to reproduce
  1. Open the Edit Event form (/events/planning/{id}).
  2. Read the subtitle under the "Basic Information" heading.
Expected: Merchant-facing help text (or none).
Actual: "Map these fields to the add-event API payload." shown to end users.
Suggested fix: Replace with merchant-friendly copy or remove the developer note.
